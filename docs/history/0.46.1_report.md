# 0.46.1 overnight review — 2026-09-19 into 2026-09-20

Supervised watch of the live deployment from 23:30 to 08:00 CEST, checking the
event log, lock ownership and the control channel at every scheduled reset.

## Verdict

**The feature released in 0.46.1 works. The outcome it exists to serve did not
happen tonight, for an unrelated defect that the watch found and that is now
fixed but not yet deployed.**

Input handover was exercised twice on the live system and behaved exactly as
designed, including the automatic re-arm. Nothing crashed, nothing typed into a
session, and every refusal during the night was a correct fail-closed refusal.

The two Codex sessions that were blocked all night were *not* continued at their
03:42 reset. The cause is not the handover work and not the quota logic: Codex
CLI 0.155.1 renders its usage banner with a typographic apostrophe (U+2019),
while `codex/limit-usage` was written with an ASCII one. With that pattern
missing, no action was proposed, the purchase-offer veto could not be suppressed
and the bounded post-reset retry never armed. **On the current Codex build, no
blocked Codex session could have been continued, whatever the quota, the policy
or the arming said.** Fixed in `336b350` (0.46.2), with regression fixtures
transcribed from tonight's screens, verified read-only against those same live
screens — and deliberately not deployed while nobody was awake to watch it.

## What failed

**Codex continuation at the 03:42 reset. Nothing happened.**

Read-only recognizer run against the two live blocked screens at 03:51:

```
state=WAITING_FOR_RESET  ids=('codex/try-again-at', 'codex/purchase-offer')
action=None              retry_prompt=False
```

Probing the wording variants (booleans only, no terminal text):

```
False  You've hit your usage limit      <- ASCII apostrophe, what the pattern had
True   You’ve hit your usage limit      <- U+2019, what Codex 0.155.1 renders
```

The failure chain, each link verified:

1. `codex/limit-usage` misses, so the only pattern carrying a `ResumeAction` never
   matches → `Recognition.action` is `None`.
2. The purchase-offer veto is suppressed only for the exact three-id banner plus a
   `TEXT_THEN_ENTER` action (`policy.py:176-191`), so it stands.
3. `retry_prompt` is `False`, because the exact banner anchor in `codex.py`
   matches on **raw** lines rather than the folded windows — a second site of the
   same ASCII apostrophe. That is what gates the opt-in bounded retry, the one
   documented path that can act when quota data cannot refresh while blocked.

Claude's patterns carry the same apostrophe in seven places, and its
`limit_headline` anchor has the same raw-line shape, so this was one character
away from being a Claude outage too.

Refusal reasons across the watch: 28 `paid-action-required:codex/purchase-offer`
(the defect above), 16 `no-recognised-blocking-prompt`, 8 `process-gone`,
6 `not-automatable:idle-shell`. Every one of them was correct given what the
recognizer could see.

### Second finding: log rotation drops the owner-only permission

The log rotated at 02:46 and the new files are world-readable:

```
agent-while-true.log.2  -rw-------   (written before the rotation)
agent-while-true.log.1  -rw-r--r--
agent-while-true.log    -rw-r--r--
```

`logging_setup.setup()` chmods the log to `0600` once, at startup
(`logging_setup.py:132`). `RotatingFileHandler` creates each successor with the
process umask, so from the first rollover onwards the live log and every backup
are readable by any local user - against the module's own stated guarantee that
"the file records which sessions the supervisor controls, which is not something
other local users need to read". Not fixed here: it deserves its own tested
commit rather than a hurried one.

### The fix — `336b350`, version 0.46.2

`normalise_typography()` in `providers/base.py` folds curly quotes, apostrophes
and non-breaking spaces onto the ASCII the patterns are written in, applied to
both match windows and to both raw-line anchors. Pattern table bumped to
`codex-0.155.x/6`, 0.155.1 recorded as verified. Fixtures
`CODEX_USAGE_LIMIT_TYPOGRAPHIC` and `CLAUDE_SESSION_LIMIT_TYPOGRAPHIC` added
before the fix, per the repository rule.

Verified read-only against the same two live sessions after the fix:

```
state=LIMIT_BLOCKED
ids=('codex/limit-usage', 'codex/try-again-at', 'codex/purchase-offer')
action=(TEXT_THEN_ENTER, 'allow_codex_auto_resume')
retry_prompt=True   reset_at=2026-09-20 01:42:00+00:00
```

Full suite 628 passed, `simulate --all` 12/12, `localPipeline.sh` PASS.

## Deliberately not done

The fix was **not** deployed overnight. Installing it would have armed
continuation that types into real Codex composers while nobody was watching, and
that is a decision for the person whose sessions they are. The service ran
0.46.1 unchanged for the whole watch.

## Recommended next steps

1. Deploy the fix and let it act on the still-blocked sessions:
   ```bash
   cd ~/repos/AgentWhileTrue
   python3 -m build --wheel -o dist
   pipx install --force dist/agent_while_true-0.46.2-py3-none-any.whl
   systemctl --user restart agent-while-true.service   # or quit and restart the TUI
   ```
   The TUI currently holds the lock, so restart whichever one you want armed.
2. Release 0.46.2 once the fix has been seen working against a real reset.
3. Restore `0600` on rotation - a `RotatingFileHandler` subclass whose
   `doRollover` re-chmods, or an `opener` that creates with `0o600`.
4. Consider a `doctor` check that warns when the installed provider CLI is newer
   than the pattern table's `VERIFIED_AGAINST`. Tonight's failure was silent:
   the recognizer simply stopped understanding the screen, and only a
   read-only probe surfaced it. A drift warning would have said so at 23:30.
5. Cosmetic: `format_reset_in` (`ui.py:188`) rounds up with `math.ceil`, so a
   17-minute wait prints as `(1h)`. Conservative by design, but it reads oddly
   next to an exact clock time.

## Follow-up — 2026-09-20 10:22, the fix proven on a real reset

0.46.2 was deployed and **all four blocked Codex sessions were continued within
two seconds of the service taking input control**:

```
10:22:21 resume_sent      action=TEXT_THEN_ENTER authorization=TIME_ONLY   (x4)
10:22:22 state_change     WAITING_FOR_RESET -> ACTIVE                      (x4)
10:22:22 resume_verified  result=resumed                                   (x4)
```

`authorization=TIME_ONLY` is the documented sole exception at work: quota was
still `STALE` because a blocked Codex session writes no new rollout data, so the
opt-in bounded retry after an anchored reset carried the action. Under 0.46.1
the same screens produced no action at all. The overnight finding is confirmed
end to end, and the recommendation to release 0.46.2 is met.

Two operational traps surfaced during the deployment and are worth fixing:

1. `pipx install --force` silently does nothing when the target venv is in use:
   uv fails to recreate it, pipx prints "Installing to existing venv" and leaves
   the old version in place. The deployment looked successful while the service
   still ran 0.46.1. `pipx uninstall` followed by `pipx install` works.
2. The unit cannot start at all while an interactive watcher holds the lock: auto
   mode exits 1 at startup, `Restart=on-failure` retries, and the unit burns its
   start limit. Starting in observe and re-arming when the lock frees - the
   behaviour 0.46.1 already implements *after* startup - would be the
   consistent choice.
